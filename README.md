# Типобезопасность на TypeScript: миграция JS-проекта в строгий режим — от any до размеченных объединений и проверки данных на границах приложения

## О проекте

В репозитории лежит небольшое веб-приложение интернет-магазина на **JavaScript**. Оно загружает
список заказов с сервера, показывает его, считает выручку, фильтрует заказы по статусу и
открывает чек заказа. В код заранее внесено **16 ошибок**. Часть из них видна сразу (вместо
сумм — `NaN`), часть проявляется только при определённых действиях пользователя.

Вы переводите это приложение на **TypeScript в строгом режиме**, находите ошибки с помощью
компилятора и добавляете проверку данных, которые приходят с сервера.

**Ориентировочное время:** 10–12 часов, включая разработку, тестирование, отчёт и видео.

> Если вы никогда не работали с TypeScript, ничего страшного: задание рассчитано именно на это.
> Все действия по шагам описаны в [пошаговой инструкции](docs/STEP_BY_STEP.md), начиная с
> установки программ.

## Цель

Научиться использовать систему типов TypeScript как инструмент поиска и предотвращения ошибок:
проектировать типы так, чтобы неправильный код не компилировался, а неправильные данные извне
отклонялись в момент получения.

## Задачи

1. Изучить проектирование типов в TypeScript: размеченные объединения, обобщённые, утилитные и
   брендированные типы ([теория](docs/THEORY.md)).
2. Включить строгий режим компилятора и перевести все модули приложения с JavaScript на
   TypeScript, не используя `any`.
3. Спроектировать типы предметной области:
   - заказ — размеченное объединение по статусу;
   - деньги, проценты и номер заказа — брендированные типы;
   - результат операции «успех или ошибка» — обобщённый тип `Result<T, E>`;
   - отчёт и подписи интерфейса — утилитные типы `Record`, `Pick`, `Readonly`.
4. С помощью компилятора найти 16 заложенных в код ошибок, исправить каждую и описать её в
   отчёте.
5. Добавить проверку ответов сервера через Zod-схему, согласованную с типом заказа, и понятные
   сообщения об ошибках загрузки.
6. Добиться прохождения всех 58 автотестов локально и на GitHub.
7. Подготовить отчёт о найденных ошибках и видеоотчёт.

## Чему научит проект

После выполнения проекта вы сможете:

- объяснить, чем строгий режим TypeScript отличается от обычного, и настроить `tsconfig.json`;
- переводить существующий JavaScript-код на TypeScript постепенно, файл за файлом, не ломая
  работающее приложение;
- читать сообщения компилятора и отличать «компилятору не хватает типа» от настоящей ошибки в
  программе;
- использовать `unknown` вместо `any` и сужать типы проверками (`if`, `instanceof`, защитники
  типа);
- описывать варианты данных размеченными объединениями и с помощью `never` проверять, что
  разобраны все варианты;
- писать обобщённые типы и функции, которые работают с любыми данными без потери типов;
- строить новые типы из существующих утилитными типами `Record`, `Pick`, `Readonly`, `Exclude`;
- создавать брендированные типы, которые не дают перепутать значения одного базового типа
  (например, сумму и процент);
- типизировать работу со страницей: элементы, события, значения полей формы;
- проверять внешние данные во время работы программы схемами Zod и связывать схемы с типами;
- работать с инструментами современной разработки: Vite, Vitest, Git, GitHub Actions.

### Темы и где они встречаются в проекте

| Тема | Где в проекте |
|---|---|
| Строгий режим TypeScript (`strict`) и отказ от `any` | `tsconfig.json`, весь код |
| Размеченные объединения (discriminated unions) | статусы заказа, виды ошибок загрузки, состояние приложения |
| Обобщённые типы (generics) | тип «успех или ошибка» `Result<T, E>`, функции `buildReport` и `getElement` |
| Утилитные типы (`Record`, `Pick`, `Readonly` и др.) | подсчёт заказов по статусам, подписи фильтра, описание ответа сервера |
| Брендированные типы | деньги `Money`, проценты `Percent`, номер заказа `OrderId` — их нельзя перепутать |
| Типы DOM и защитники типа (type guards) | поиск элементов страницы, обработка кликов, значения выпадающих списков |
| Проверка данных на границе приложения | Zod-схема проверяет ответ сервера в момент получения, до того как данные попадут в программу |

Теория по всем темам с примерами — в [docs/THEORY.md](docs/THEORY.md).

## Сценарий работы приложения

1. Пользователь открывает страницу. Приложение показывает «Загружаем заказы…» и запрашивает
   список заказов у учебного сервера.
2. После загрузки показываются список заказов (номер, покупатель, статус, сумма) и сводка:
   количество заказов и выручка.
3. Выпадающий список «Статус» оставляет в списке только заказы с выбранным статусом.
4. Клик по заказу открывает его чек справа.
5. Переключатель «Сервер» меняет поведение учебного сервера: «нормальный», «присылает
   неправильные данные», «отвечает ошибкой 500». При ошибке приложение показывает понятное
   сообщение и не показывает устаревшие данные.

## Учебный сервер

Приложение получает заказы по адресу `/api/orders`. На этот запрос отвечает маленький учебный
сервер из `server/mock-api.ts`, который запускается вместе с `npm run dev`. Режим сервера
переключается прямо в интерфейсе, в правом верхнем углу:

| Режим | Что присылает сервер |
|---|---|
| нормальный | правильный список заказов (`data/orders.json`) |
| присылает неправильные данные | заказы с ошибками: неизвестный статус, цена строкой (`data/orders-broken.json`) |
| отвечает ошибкой 500 | ошибку сервера вместо данных |

Сервер изображает «чужой» сервер, на который мы не можем повлиять, поэтому папку `server/`
менять не нужно.

## Правила

- **Тесты в папке `tests/` менять нельзя.** Проверяющий запускает работу на исходных тестах.
  Свои тесты кладите в `extra-tests/`.
- **Нельзя использовать `any`**, `// @ts-ignore`, `// @ts-nocheck` и `// @ts-expect-error` в `src/`.
  Это проверяют тесты.
- **Нельзя ослаблять `tsconfig.json`**: строгие проверки должны быть включены. Это тоже проверяют
  тесты.
- Не используйте оператор `!` (например, `order!.id`) и приведения `as`, чтобы «заглушить»
  компилятор. Тесты это не ловят, но это влияет на уровень оценки (см. Б+).

## Обязательные имена

Тесты импортируют из ваших файлов определённые типы и функции, поэтому называть их нужно ровно
так:

| Файл | Типы | Функции и значения |
|---|---|---|
| `src/result.ts` | `Result<T, E>` | `ok`, `err` |
| `src/money.ts` | `Money`, `Percent` | `money`, `percent`, `sumMoney`, `multiplyMoney`, `applyDiscount`, `formatMoney` |
| `src/order.ts` | `Order`, `OrderStatus`, `OrderId` | `orderId`, `orderTotal`, `statusLabel`, `trackingNumber`, `customerContact`, `findOrder` |
| `src/schemas.ts` | — | `OrderSchema`, `OrdersSchema` |
| `src/api.ts` | `ApiError` | `fetchOrders` |
| `src/report.ts` | — | `buildReport`, `orderReceipt` |
| `src/ui/app.ts` | — | `startApp` |

Свои дополнительные типы и файлы добавлять можно.
