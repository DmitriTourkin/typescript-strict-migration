# Критерии оценки

Работа оценивается по уровням:

| Уровень | Что это значит |
|---|---|
| **Б−** | базовый уровень, выполнен минимум: переведена и исправлена логика приложения |
| **Б** | базовый уровень: выполнена вся обязательная часть задания |
| **Б+** | базовый уровень, выполнен качественно: аккуратные типы, подробный отчёт |
| **П** | продвинутый уровень: уровень Б+ и две дополнительные задачи из [списка П](#задачи-уровня-п) |
| **Э** | экспертный уровень: уровень П и две дополнительные задачи из [списка Э](#задачи-уровня-э) |

Уровни идут по нарастанию: чтобы получить уровень, нужно выполнить **все** требования
предыдущих уровней и требования этого уровня.

При сдаче напишите, на какой уровень вы претендуете и какие дополнительные задачи выполнили
(см. [порядок сдачи](../README.md#порядок-сдачи)).

## Обязательная часть: уровни Б−, Б, Б+

2. На TypeScript переведены и исправлены модули логики: `result`, `money`, `order`, `schemas`,

3. `npm run typecheck` завершается без ошибок.
4. В переведённых файлах нет `any`, `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`.
5. Проходят все тесты блоков 1–5: «Деньги», «Заказы», «Загрузка заказов», «Zod-схемы», «Отчёты»
   (39 тестов). Проверить: `npm test`, в выводе у этих блоков нет `×`.
6. В `REPORT.md` описаны **не менее 8** найденных ошибок: файл, код ошибки компилятора, как она
   проявлялась, как исправлена. Заполнен раздел про Zod.
7. Записано видео (интерфейсная часть в нём может отсутствовать).

### Б — обязательная часть выполнена полностью

Всё из Б−, а также:

2. `npm run check` проходит: **58 из 58 тестов**.
3. Проверка на GitHub (вкладка **Actions** вашего репозитория) зелёная.
4. В `REPORT.md` описаны **все 16** заложенных ошибок по шаблону, в разделе про Zod есть

### Б+ — обязательная часть выполнена качественно

Всё из Б, а также:

4. История в Git ведётся по шагам: не меньше 8 коммитов с понятными сообщениями, а не один
   коммит в конце.
5. В `REPORT.md` содержательно заполнены разделы 4 и 5: как и почему вы спроектировали типы
   (с фрагментами кода), сравнение ошибок, найденных «на глаз» и компилятором, какие ошибки
   TypeScript не может найти.

### Задачи уровня П

Для уровня **П** выполните уровень Б+ и **любые две** задачи из этого списка.

#### П1. Дополнительные проверки компилятора

Включите в `tsconfig.json` четыре дополнительные настройки и исправьте все ошибки, которые они
найдут:

| Настройка | Что проверяет | Документация |
|---|---|---|
| `exactOptionalPropertyTypes` | необязательное поле `x?: string` нельзя явно задать как `undefined`, если это не разрешено в типе | [ссылка](https://www.typescriptlang.org/tsconfig/#exactOptionalPropertyTypes) |
| `noUnusedLocals` | неиспользуемые переменные | [ссылка](https://www.typescriptlang.org/tsconfig/#noUnusedLocals) |
| `noUnusedParameters` | неиспользуемые параметры функций | [ссылка](https://www.typescriptlang.org/tsconfig/#noUnusedParameters) |
| `noPropertyAccessFromIndexSignature` | к полям объектов вида «ключ — значение» нужно обращаться через `obj["key"]` | [ссылка](https://www.typescriptlang.org/tsconfig/#noPropertyAccessFromIndexSignature) |

**Готово, если:** `npm run check` проходит с этими настройками. В отчёте для каждой найденной
ошибки объяснено, о чём она и почему исправление правильное.

#### П2. Линтер с проверкой типов

Линтер — программа, которая находит в коде подозрительные места, которые не являются ошибками
типов. Подключите [ESLint](https://eslint.org/) с [typescript-eslint](https://typescript-eslint.io/).

1. Установите пакеты:
   ```bash
   npm install -D eslint@9 typescript-eslint
   ```
2. Создайте в корне проекта файл `eslint.config.js`:
   ```js
   import tseslint from "typescript-eslint";

   export default tseslint.config({
     files: ["src/**/*.ts"],
     extends: [tseslint.configs.recommendedTypeChecked],
     languageOptions: {
       parserOptions: { projectService: true, tsconfigRootDir: import.meta.dirname },
     },
     rules: {
       "@typescript-eslint/no-explicit-any": "error",
       "@typescript-eslint/no-non-null-assertion": "error",
       "@typescript-eslint/switch-exhaustiveness-check": "error",
     },
   });
   ```
3. Добавьте в `package.json` скрипт `"lint": "eslint src"` и включите его в `check`:
   `"check": "npm run typecheck && npm run lint && npm test"`.
4. Исправьте всё, что найдёт `npm run lint`. Отключать правила или добавлять комментарии
   `eslint-disable` нельзя.

**Готово, если:** `npm run lint` завершается без ошибок, `npm run check` и проверка в Actions
проходят. В отчёте описано, что нашёл линтер и почему этого не нашёл компилятор.

#### П3. Собственные тесты, включая тесты типов

Напишите свои тесты в папке `extra-tests/`:

1. **Не меньше 8 тестов поведения** (файлы `*.test.ts`). Обязательно покройте:
   защитники типа `isStatusFilter` и `isServerMode`; `getElement` с элементом не того типа;
   граничные значения `money` и `percent` (0, 100, дробные, отрицательные); `errorMessage`
   для всех трёх видов ошибок.
2. **Не меньше 6 проверок типов** (файлы `*.test-d.ts`) с помощью
   [`expectTypeOf`](https://vitest.dev/guide/testing-types): например, что `Money` нельзя
   получить из `number`, что после проверки `result.ok` доступно `value`, что `OrderStatus` —
   это ровно четыре статуса.

Запуск: `npm test` (тесты поведения) и `npm run test:types` (тесты типов).

**Готово, если:** обе команды проходят. В отчёте есть скриншот, где тест типов **падает**, если
временно сделать `Money` обычным `number`: это доказывает, что тест действительно что-то
проверяет.

#### П4. Сортировка списка заказов

Добавьте в интерфейс выпадающий список «Сортировка» рядом с фильтром статуса:

| Значение | Подпись | Порядок |
|---|---|---|
| `none` | Как на сервере | без сортировки (по умолчанию) |
| `total-asc` | Сумма ↑ | по `orderTotal`, от меньшей к большей |
| `total-desc` | Сумма ↓ | по `orderTotal`, от большей к меньшей |
| `customer` | Покупатель | по имени покупателя, по алфавиту (`localeCompare`) |

Требования к типам:

- тип `SortKey` — объединение четырёх значений;
- подписи — `Record<SortKey, string>`, функции сравнения —
  `Record<Exclude<SortKey, "none">, (a: Order, b: Order) => number>`;
- значение из `<select>` проверяется защитником типа `isSortKey`;
- сортировка не меняет исходный массив заказов: сортируйте копию, `[...orders].sort(compare)`.

**Готово, если:** сортировка работает вместе с фильтром, по умолчанию порядок как на сервере
(тесты задания на это рассчитывают), в `extra-tests/` есть не меньше 3 тестов сортировки.

### Задачи уровня Э

Для уровня **Э** выполните уровень П и **любые две** задачи из этого списка.

#### Э1. Вторая граница данных: адрес страницы

Адрес страницы — тоже данные «извне»: пользователь может вписать туда что угодно. Сохраняйте
выбранные фильтр статуса и режим сервера в адресе (`?status=paid&mode=broken`) и
восстанавливайте их при открытии страницы.

- Читайте параметры через `URLSearchParams` и **проверяйте Zod-схемой**. Некорректное
  значение (например, `?status=refunded`) не должно ломать приложение: используйте значение по
  умолчанию.
- Обновляйте адрес без перезагрузки страницы: `history.replaceState`.
- Документация: [URLSearchParams](https://developer.mozilla.org/ru/docs/Web/API/URLSearchParams),
  [History.replaceState](https://developer.mozilla.org/ru/docs/Web/API/History/replaceState).

**Готово, если:** открытие страницы по адресу с параметрами восстанавливает фильтр и режим,
неверные параметры игнорируются, в `extra-tests/` не меньше 4 тестов (корректные значения,
неверные значения, отсутствие параметров, обновление адреса при выборе в `<select>`). В отчёте
объяснено, почему адрес страницы — это граница приложения.

#### Э2. Конечный автомат состояния приложения

Сейчас состояние меняется присваиваниями `state = ...` в разных местах `app.ts`. Сделайте
изменения состояния явными:

- опишите события как размеченное объединение `AppEvent`, например
  `{ type: "load_started" } | { type: "load_failed"; error: ApiError } | { type: "load_succeeded"; orders: Order[]; report: Report }`;
- напишите чистую функцию `transition(state: AppState, event: AppEvent): AppState` в отдельном
  файле `src/ui/state.ts`. Внутри — `switch` по `event.type` с проверкой полноты через `never`;
- в `app.ts` состояние меняется только через `transition`.

**Готово, если:** `app.ts` не содержит присваиваний `state = { ... }` кроме
`state = transition(state, event)`, в `extra-tests/` не меньше 6 тестов `transition` без DOM
(в том числе: ошибка после успешной загрузки не оставляет старых заказов). В отчёте объяснено,
какие ошибки такая организация предотвращает.

#### Э3. Обобщённый слой загрузки данных с таймаутом

1. Напишите обобщённую функцию
   `fetchJson<T>(fetchFn: FetchFn, url: string, schema: z.ZodType<T>): Promise<Result<T, ApiError>>`,
   которая делает запрос, проверяет ответ схемой и возвращает `Result`. Перепишите
   `fetchOrders` через неё. Публичный интерфейс `fetchOrders` и тип `ApiError` менять нельзя:
   на них рассчитаны тесты задания.
2. Добавьте таймаут: если сервер не ответил за 5 секунд, запрос отменяется через
   [AbortController](https://developer.mozilla.org/ru/docs/Web/API/AbortController), и
   возвращается ошибка `{ kind: "network", message: "Сервер не ответил за 5 секунд" }`.
   `FetchFn` получает второй, необязательный параметр `{ signal?: AbortSignal }`, поэтому
   подделки сервера из тестов задания продолжают подходить.

**Готово, если:** тесты задания проходят, в `extra-tests/` не меньше 3 тестов `fetchJson` и
таймаута. Для таймаута используйте
[поддельные таймеры Vitest](https://vitest.dev/guide/mocking#timers) (`vi.useFakeTimers`),
чтобы тест не ждал 5 секунд.
